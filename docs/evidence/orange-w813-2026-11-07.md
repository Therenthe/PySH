`42ac4d908b9285e72d43155e0182f7a5bc940290`; no runtime or OS changes.
Native Raspberry Pi 4, Debian 13 arm64, Chromium 154.0.8037.92,
loaded Widevine 4.10.3112.0, 800×480. The user authenticated and explicitly
authorized selecting the sole existing Orange member. No account fields,
cookies, profile contents or license payloads were inspected.

Charter: reproduce the named channel, distinguish capability from playback,
observe only bounded player/codec/status metadata, preserve the account and

forward were loopback-only. MPD parsing retained only codec, dimensions and

## What the evidence does and does not establish

The observed manifest offered AVC/H.264 at 854×480, 1280×720 and 1920×1080,
with AAC audio. MSE recognizes the AVC/AAC types. Actual Orange negotiation
accepted video `SW_SECURE_DECODE` and `SW_SECURE_CRYPTO`, and audio
`SW_SECURE_CRYPTO`. An earlier combined audio/video robustness probe must not
be interpreted as lack of video-only `SW_SECURE_DECODE` support.

Observed key status was `usable`; no `output-restricted` or `internal-error`
status was observed. This does not prove every required stream reference is
authorized. No key values or identifiers were collected. Successful EME
preparation, HTTP 200 responses and a catalogue are not playback acceptance.

RxPlayer 4.3.0 can emit this error when video representations are unsupported
or marked undecipherable. Orange's content-wide license handling can also
exclude references absent from the usable set. That is a source-supported
hypothesis, not a demonstrated root cause here. The comparison reported by
the user points toward device/browser compatibility, without proving a
particular DRM policy, HDCP requirement or provider-side defect.

Classification: unresolved native playback compatibility failure, rather
than a demonstrated PySH navigation defect. No workaround, browser identity
change, license-policy change, profile reset or package replacement was made.
Orange playback remains **FAIL/OPEN**; the integration controls retain their
separate scoped results. Full product acceptance remains OPEN.

## Extension isolation and video decipherability

A subsequent native run used the same existing authenticated profile with
`--disable-extensions`, no EME hooks and ordinary official channel selection.
The saved Sport grid and the error screenshot both identify Prima Sport 1.
The player still raised fatal video `NO_PLAYABLE_REPRESENTATION` / W813 and
decoded zero frames. The final grid view in that run means the player was
closed; its final `visibleW813:false` is not successful playback. An independent
review confirms this boundary. This isolates the failure from the active PySH
extension, without establishing a provider-specific root cause.

A bounded, passive breakpoint on the hash-verified public RxPlayer script then
observed the video adaptation immediately before the failure:

| Video adaptations | Representations | Codec supported | Marked decipherable | Marked undecipherable | Playable |
| --- | --- | --- | --- | --- | --- |
| 1 | 3 | 3 | 0 | 3 | 0 |

The inspector returned only type enums and aggregate counts. It used V8's
side-effect check, then resumed execution and removed the breakpoint. No
identifiers, URLs, protection references or key/license data were collected.
The public script SHA-256 was
`93701f7103d5156ef81fa3dae9098e37f1cb04e6c67bc9b9a855711a096733ff`.

This narrows the observed failure: the player accepts the codecs and excludes
all video representations through its decipherability state. It does not prove
which license policy, reference association or platform behavior caused that
state. The user additionally confirms same-account playback on both Windows
and Android; these comparisons remain user reports.

Private records are in `.runtime/orange-isolation-20261107/` and
`.runtime/orange-representations-20261107/`. Each owned browser/tunnel was
closed after its run. Radio was resumed only when the same station remained
paused by the probe; user changes to station, pause or levels were preserved.

Its browser files are prepared side by side as a diagnostic candidate, with
normal sandboxing and a separate profile. No maintainer scripts, APT source
changes, Chromium replacement or account imports were performed. Runtime and
the original authenticated profile remain unchanged.

Native readiness observed: actual Widevine/AAC/H.264 capability, existing PySH
extension loaded for the trial, native keyboard visible with an 800×240 web

The current trial loads it explicitly; a supported persistent production setup
would be required before any Chrome delivery. The user completed the new Orange
login directly on the device. Authentication fields and login screenshots were
not collected.

The authenticated Chrome 157 trial selected Prima Sport 1 from a separately
captured Sport grid. The player logo and programme title identify the channel

authenticated profile did not resolve this failure. This remains a failed
compatibility trial, not a delivered fix. The browser/tunnel closed, settings
were unchanged, and the new account profile was retained.
